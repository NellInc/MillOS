# Blender prompts — MillOS

Two modes, two jobs. Pick by what the output has to survive.

| Task | Mode |
|---|---|
| Anything that becomes a committed asset or pipeline step | **headless** |
| Verifying a glTF contract, budgets, bounds, regressions | **headless** |
| Designing geometry that ships as procedural TS | **headless** to finalise, **MCP** to explore |
| "What would this shape look like" | **MCP** |
| Poking at a `.blend` you already have open | **MCP** |

The deciding fact for this repo: MillOS machines are **procedural instanced geometry in TypeScript**, not GLBs. Validated Quaternius CC0 characters supply anonymous local workers and residents. Forklift glTF file order remains load-bearing. The no-human constraint concerns automated testing; it does not prohibit simulated people or the scarecrow. Vehicles remain autonomous, without real-person likenesses or recorded voices. Most Blender work here therefore ends as TS or as a pipeline change, not as a new `.glb`.

## Headless prompt

```
Use headless Blender for this: /Applications/Blender.app/Contents/MacOS/Blender
--background --python <script> -- <args>. Write the script under
scripts/blender/ so it is re-runnable and reviewable; do not do this work
interactively.

Constraints specific to MillOS — treat these as hard:

1. NEVER round-trip a pipeline GLB through Blender. public/models/*.glb are
   generated by scripts/normalize-model-assets.mjs from assets/source/models/.
   A measured Blender round trip of the forklift permutes glTF animation order
   AND mesh order. Animation clips are mapped by source name and mesh names
   carry load-bearing index suffixes that runtime code matches on
   (forklift-hydraulic02-poles-19 in src/components/models/ForkliftModel.tsx).
   Reordering silently swaps fork raise/lower and kills the telescoping ram.
   If geometry must be reduced, do it in the pipeline with
   simplifyPrimitive/meshopt, not in a modeller.

2. assets/source/models/ is immutable provenance. Read it; never write it.

2a. Use the approved CC0 local character assets for workers and residents. Keep
    vehicle operation autonomous and exclude real-person portraits and voices.
    Working if the community delivery gate admits only the licensed local roster.

3. Blender's world is Z-up; three.js is Y-up. If you build a lathe or profile
   Y-up to match the runtime, an unrotated Blender camera frames it correctly.
   Getting this wrong renders a blank frame.

4. New scene geometry should usually land as procedural TypeScript, matching
   the surrounding code, not as a loaded asset. Machine geometry is shared
   module-level constants instanced across every machine. If you author a
   shape in Blender, port the final profile into TS and keep the Blender
   script as the design/preview tool.

5. If the geometry is unit-normalised for instancing, keep the envelope exact
   (e.g. max radius 1.0, y in [-0.5, 0.5]) so existing instance matrices and
   neighbouring parts still line up.

6. If a dense geometry is used by an InteractiveInstances mesh, it is raycast
   on EVERY pointer move. Measure it. Anything over a few hundred triangles
   needs a cheap picking proxy (see raycastSiloShell in CompactMachines.tsx),
   or hovering will eat the frame budget.

Existing tools: scripts/blender/glb_report.py dumps the glTF file-order
contract (animations, materials, meshes, nodes) for before/after diffing.
inspect_forklift.py reports per-object vertex counts. silo_profile_preview.py
renders a geometry comparison. forklift_lod.py is the round-trip reproducer
for constraint 1 — keep it, do not "fix" it into the pipeline.

machine_part_preview.py is the general version of silo_profile_preview and the
one to reach for first: `--part <name>` (or `--all`) rebuilds a part exactly as
three.js would, next to a proposal, at the part's real instance scale and
viewing distance. It prints vertex/triangle counts and per-axis half-extents,
and flags any envelope DRIFT in millimetres on the axis that moved. Add new
parts to its PARTS table rather than writing another one-off script.

Two traps it exists to catch, both of which produced a wrong answer first time:
three.js orients a torus with the ring in XY and the tube along Z (so building
it in XZ applies a squashed instance scale to the wrong axis), and a part's
envelope must be compared per axis — scaling a drift by the largest scale
component reported a 1.2 mm change as 10.5 mm.

Verify before claiming done, and show the output:
  npm run validate:assets     # asset gate: bounds, budgets, required nodes/clips
  npm run typecheck && npm run lint
  npm run build
  npm test                    # record the live baseline; do not copy stale counts
And for anything visible or interactive, actually run it — the repo rule is
that a build is not a runtime. Load the dev server and confirm in the scene.

Report measured numbers (vertices, bytes, microseconds), not impressions.
```

## MCP prompt

Requires Blender's **GUI** open, the BlenderMCP addon enabled, and `N` → BlenderMCP → **Connect to Claude** (port 9876). Headless Blender does not serve this.

```
Use the Blender MCP for exploration only. The goal is a decision — a profile,
a proportion, a silhouette — not a committed artefact.

Rules:

1. Do not open, modify, or export anything under assets/source/models/ or
   public/models/. Those are provenance and pipeline outputs; the MCP mutates
   the live scene and leaves no reviewable diff.

2. Work in a scratch scene. Assume whatever is open belongs to the user.
   Do not save over it.

3. Do not trigger modal dialogs or operators that block on user input — they
   freeze the socket and the session stops responding.

4. Build Y-up to match three.js, so what you see maps to the runtime.

5. When the shape is decided, STOP and port it: either into a
   scripts/blender/*.py script or, more usually here, into procedural
   TypeScript geometry. State the final numbers explicitly (segment counts,
   amplitudes, radii, envelope bounds) so they can be transcribed exactly.

Good uses: tuning a corrugation pitch or ridge depth by eye, checking a
silhouette at a realistic camera distance, judging whether added detail reads
at all before paying for it, quick lookdev on a material idea.

Bad uses: producing a runtime asset, editing pipeline inputs, anything whose
correctness depends on a diff or a repeatable measurement.
```
